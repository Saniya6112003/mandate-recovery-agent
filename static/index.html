What it solves

UPI Autopay doesn't fail like a card does

Card-mandate recovery is a solved product category. UPI Autopay is a different problem — it needs a real-time bank approval on every debit, so it fails far more often, for reasons that have no card equivalent, under rules that constrain what you're even allowed to do next.

₹

Revenue leaks silently

Every failed autopay debit is money a merchant has already earned. Recovery is usually a blind retry loop that ignores why the debit failed.

⚠

The codes are rail-specific

IE funds blocked by another mandate, VA revoked, QA paused by user, MA0 not present. A generic "payment failed" abstraction can't reason about any of them.

§

Compliance limits the fix

A 24-hour pre-debit notice, revocable vs non-revocable state, retry caps. These are legal boundaries, not retry heuristics — and a revoked mandate simply cannot be debited.

How it works

Five stages. The third one can overrule the AI.

Watch a failed debit move through the system. The compliance stage is ordinary deterministic code — it reads authoritative mandate state, not the model's opinion, so it catches an unsafe action even when the AI is confidently wrong.

1

Debit fails

The bank returns an NPCI decline code with amount and retry history.

2

AI diagnoses

Infers the cause, proposes one bounded action, states its confidence.

3

Rules check it

RBI limits, retry caps, exposure ceilings. This stage always wins.

4

Action executes

A real Razorpay Payment Link, a scheduled retry, or a human handover.

5

Outcome recorded

Written to an immutable audit row. Recovered only on verified proof.

Measured money

The number only moves on proof

A real test-mode payment of ₹9,999 was made. Razorpay confirmed it. Our audit log refused to count it — because no signature-verified webhook had arrived yet.

Before the webhook
outcome: pending

Razorpay's API said paid. We still didn't count it. Trusting an API poll or our own call succeeding is exactly the self-reported number this project exists to avoid.

After the webhook
outcome: recovered

Razorpay signed and delivered payment_link.paid, the HMAC verified, and only then did the rupee figure move. Same system, same money — proof was the difference.

Idempotent by construction

Razorpay warns duplicate deliveries happen. event_id is a Postgres PRIMARY KEY with ON CONFLICT DO NOTHING, so a double-delivery cannot double-count a recovery even if the application misbehaves.

It under-reports on purpose

When proof is missing the case stays pending — never an optimistic guess. A recovery figure that overstates is worse than one that waits.

Build challenges

What broke, and how it was fixed

Every one of these was found by testing against the real thing rather than by reading code. Several would have failed live on camera.

1The decline codes were fabricated›

The first dataset used codes like RC01 and MD21 — plausible-looking, but not real UPI codes. They were card-style ISO 8583 codes with invented prefixes. Any payments engineer would have spotted it instantly.

Fixed: every code re-verified against Axis Bank's published UPI response code list and replaced. The unknown bucket now holds genuinely ambiguous codes, so those cases can't be solved by lookup.
2The guardrail was reading the answer key›

The compliance check tested true_cause — a ground-truth label that exists only for scoring. It worked, but it was indefensible: a reviewer would rightly call it cheating.

Fixed: added a mandate_status field representing what an authoritative bank lookup returns. The guardrail reads that; the model never sees it. Strictly stronger — it now blocks unsafe retries even when the diagnosis is wrong.
3The demo worked exactly once›

Razorpay requires a unique reference_id. We'd set it to the mandate ID, so the second run failed with "payment link already exists". Conceptually wrong too — a retry sequencer makes multiple attempts per mandate by design.

Fixed: the reference is now per-attempt, and the webhook resolves the mandate back from the link's notes. Verified by running identical mandates twice against the live API.
4The test suite was calling the live API›

load_dotenv() runs at import, so once real credentials were present, every pytest run created real Payment Links on the account and burned the rate limit. Test fixture IDs were visible in the live dashboard.

Fixed: a session-wide fixture strips credentials, plus a regression test that fails loudly if anything tries to build a live client. Suite runtime dropped 3.2s → 0.94s, confirming the calls had been real.
5The model was hallucinating the code book›

With only the raw code as input, accuracy was 42%, and every failure was a code the model had never learned — it read IE as "Invalid Entity" when it means funds blocked against another mandate. Worse, it was confident while wrong, so the escalation threshold never fired.

Fixed: supplied the verified NPCI reference in the prompt — the banks' own descriptions, deliberately not the cause labels. Accuracy went 42% → 95%+, and tests now fail if a description ever leaks a cause label.
6One malformed response killed a 60-case run›

Thirty-six cases in, the model emitted "confidence": 0. nine — a number written as words. The schema guarantee worked and rejected it, but the exception propagated and destroyed the remaining 24 cases. An agent built around graceful degradation crashed on a bad payload.

Fixed: malformed generations are retried, and any undecidable case becomes a zero-confidence decision routed to human review and recorded — the batch continues, and the failure is itself auditable.
7The "immutable" audit log wasn't durable›

The log was an append-only file. Append-only describes how you write, not whether it survives. A redeploy rebuilt the container on ephemeral storage and destroyed a webhook-verified ₹9,999 recovery — the evidence for the project's central claim, lost to a routine deployment.

Fixed: a Postgres backend behind the same interface, selected by DATABASE_URL. It also closed a requirement a file could never meet — a real uniqueness constraint on event_id, enforced by the database.
8The network blocked every tunnel›

Webhook testing needs a public URL. ngrok, Cloudflare Tunnel, localhost.run, serveo and pinggy were all reset at the ISP across ports 22 and 443 — deep packet inspection on SSH, not simple hostname blocking. Later, a webhook also timed out against a sleeping free-tier instance.

Fixed: diagnosed per-host rather than assuming general failure, then deployed to a public endpoint instead of tunnelling. On the cold-start timeout the system behaved correctly — the case stayed pending rather than guessing.
